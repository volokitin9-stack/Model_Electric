# Spec Import Agent

Агент, который собирает данные из Excel-спецификаций чертежей жгутов
(`specs/Wiring_N/Wiring_N_spec.xlsx`, генерирует `tools/build_specs.py`)
и передаёт их в проекты «Модельной электрики» через REST API сервера —
тот же, которым пользуется веб-интерфейс. Прямого доступа к базе у агента
нет, поэтому вся валидация сервера (zod, проверка дублей артикулов)
работает и для него.

## Что куда попадает

| Excel (лист) | Проект «Модельной электрики» |
|---|---|
| «Чертёж»: марка, модель | **Project**: название `{Марка} {Модель} — проводка ТСУ`, артикул `ME-<МАРКА>-<МОДЕЛЬ>` (как у существующих, напр. `ME-LADA-VESTA-NG`) |
| «BOM»: P/N, кол-во, ед. | **ProjectComponent** (вкладка «Комплектующие» проекта): одна строка на P/N, количество суммируется по всем листам чертежа; в комментарии — откуда взято (`Чертёж №2: 2-1 поз.1 — 1 шт; 2-3 поз.1 — 1 шт`) |
| «Каталог»: описание, производитель, серия, сечение, аналог, источник | **ComponentCatalog** (общий каталог): наименование = описание из каталога, описание = производитель · серия · сечение, комментарий = статус по каталогу · аналог · ссылка на источник; категория — по типу позиции (корпуса разъёмов / контакты и наконечники / уплотнители и заглушки / провода и кабели) |
| Статус P/N | статус позиции: Подтверждён → `confirmed`, Вероятно → `needs_review`, Проверить → `searching`, — → `not_defined` |
| «Чертёж» (листы), «Разъёмы», «Распиновка», «Замечания» | **ProjectDrawing** + DrawingConnector / DrawingPin / DrawingNote — вкладка «Электросхемы» проекта: описание листов, таблица разъёмов, распиновка (с фильтром по листу и подсветкой проблем сечения), замечания с рекомендациями |

Позиции без P/N (провода, кабели в чертеже №1) получают артикул по
наименованию — с пометкой «P/N в чертеже не указан» в комментарии.

У **нового** проекта агент сразу ставит «Разработка схемы» = «Завершено»
(спецификация по чертежу есть) и «Поиск разъёмов» = «Завершено», только
если все P/N подтверждены по каталогу, иначе «В работе».

Чертёж загружается одним запросом `PUT /api/projects/:id/drawings/:№`
и заменяется целиком, только если содержимое файла изменилось (сервер
сравнивает хеш) — тогда же в «Истории» проекта появляется запись
«Чертёж загружен/обновлён». Чертёж привязан к одному проекту; если в
`projectMap` указать другой проект, чертёж переносится туда.

## Этап «Свод цен»

После чертежей агент загружает свод цен поставщиков разъёмов из
`export/price_import.json`. Этот файл собирает `tools/build_upload.py` из
`sources/` (свод цен поставщиков и план разработок с продажами Ozon).
Вместе с ним в `export/Model_Electric_upload.xlsx` лежит та же выгрузка для людей.

| price_import.json | Проект «Модельной электрики» |
|---|---|
| `suppliers` (Ylcn, HD Connector, JINGMING, Star technology, Jiangsu Xing Yao Electric, YBConnector, QCLNC, OLT) | **Supplier**: поиск по названию, новые получают следующий код `SUPnn`, страна Китай, валюта CNY |
| `offers`: OEM, артикул поставщика, MOQ, цена | **SupplierCrossReference** + **SupplierPrice** (CNY) к позиции каталога с тем же OEM. Номера сравниваются без дефисов и пробелов: `19296271` = `1-929627-1`, `7282885130` = `7282-8851-30`. Если номера нет ни в одном чертеже, позиция создаётся в каталоге («Корпуса разъёмов») |
| `projects`: согласованные в работу модели из «Плана разработок» (зелёная заливка) | **Project**: по чертежу модели, по `priceProjectMap` из `project-map.json`, по артикулу или названию. Если ничего не найдено, проект создаётся: `{Марка} {Модель} {Поколение} — проводка ТСУ` |
| `projects[].lines`: разъёмы комплекта и лучшая цена | **ProjectComponent**: основное предложение = лучшая цена, плановая цена в CNY, комментарий «Свод цен: …». Новые позиции получают статус `selected`; при расхождении с чертежом (Vesta 174922-1 против -2, Polo 5G0 против 5K0) — `needs_review`; альтернативный вариант (Granta 3C0 972 733 / 1J0 972 926) — `not_required`, чтобы не попасть в стоимость, пока вариант не выбран |

**Топ продавцов Ozon** — лист «Исходник» плана разработок, `projects[].ozon`
в `price_import.json`. По каждому согласованному проекту берутся 5 товаров
модели с наибольшим числом заказов. Они попадают в **ProjectCompetitor**
(блок «Топ-продавцы Ozon» на вкладке «Обзор»): продавец, товар, ссылка,
средняя цена (RUB). В комментарий пишется `Ozon #место: заказано N шт на S ₽ ·
мин. цена · бренд · категория · схема · карточка с …`. Если в один проект ведут
несколько строк плана (Granta SE и LB → чертёж №4), их товары объединяются.
Агент обновляет и удаляет только свои записи (комментарий начинается
с `Ozon #`), добавленные вручную не трогает. Модели, которые в «Исходнике»
называются иначе, сопоставляет `OZON_ALIAS` в `tools/build_upload.py`.

Цена разъёма в своде — это комплект на разъём: корпус, пины и необходимые
допы. Поэтому пины из BOM чертежа, у которых каждый корпус есть в своде
с ценой, получают плановую цену 0 CNY. В комментарий дописывается
` | Свод цен: входит в цену разъёма …`. Тогда стоимость проекта не
выглядит «частичной» из-за пинов. Без цены остаются наконечники
(DJ451-1, Cargen) и разъёмы блока (KLS, 12058980): в своде их нет.
При обновлении из чертежа этот хвост комментария сохраняется.

Правила те же, что у чертежей: количество и статус существующих позиций
не меняются, основное предложение и плановая цена заполняются, только
если пусты, комментарий перезаписывается, только если его писал этот этап
(начинается с `Свод цен:`). Новая цена кроссировки добавляется, только
если отличается от текущей (цена или MOQ). Тогда же она попадает в
историю цен. Повторный запуск на том же файле ничего не меняет.

Обновить свод: положить новые файлы в `sources/`, выполнить
`python3 tools/build_upload.py`, закоммитить `export/` и задеплоить.
После этого нажать «Обновить данные».

Флаги: `--prices <файл.json>` — другой файл; `--no-prices` — пропустить этап.
С `--drawing N` этап «Свод цен» не выполняется.

## Правила обновления (повторный запуск безопасен)

Агент идемпотентен: повторный запуск на тех же файлах ничего не меняет.
При изменении чертежа:

- **количество** берётся из чертежа (чертёж — источник правды);
- **статус** позиции только повышается (P/N подтвердили в новой версии
  чертежа → `confirmed`), но никогда не понижается — то, что выставил
  человек в вебе, агент не откатывает; `not_required` не трогает вовсе;
- **комментарий** позиции перезаписывается, только если его писал сам
  агент (начинается с `Чертёж №`) — ручные комментарии сохраняются;
- **каталог**: у существующего комплектующего дополняются только пустые
  поля (описание, комментарий, категория);
- позиции, которые есть в проекте, но пропали из BOM, по умолчанию
  только показываются в отчёте; с `--prune` удаляются — и только те,
  что были добавлены агентом по этому же чертежу.

## Как агент находит существующий проект

1. явная привязка `projectMap` — из `project-map.json` (в репозитории) и
   `config.json` (локально, приоритетнее): `{"<№ чертежа>": "<артикул, id или название проекта>"}`;
2. проект, в который этот чертёж уже загружен;
3. совпадение артикула;
4. точное совпадение названия.

Нечёткое совпадение не используется: если найден «похожий» проект
(та же марка и модель в названии, напр. «Volkswagen Polo 5» для чертежа
«Polo V SD 2010-2020»), агент пишет об этом в отчёте и создаёт новый —
чтобы привязать к существующему, добавьте его в `projectMap`.

Принятые решения (файл `project-map.json`):

- чертёж №6 «Polo V SD 2010-2020» → существующий проект **Volkswagen Polo 5** (`ME-VW-POLO5`) — это один проект;
- чертёж №9 «Largus 2012-2021» — **отдельный** проект, не «Largus 2021-»
  (тот — чертёж №10); предупреждение о похожем проекте для него не выводится
  (`separateProjects`).

## Запуск

Нужен Node.js 18+ и запущенный сервер (`apps/server`, см. README в корне)
с миграцией `project_drawings` (применяется сама при деплое —
`prisma migrate deploy` в команде запуска Docker-образа). Агент можно
направить и сразу на облачный сервер: `--server https://....onrender.com`.
Если на сервере задан `API_KEY` (обязательно для публично задеплоенного
сервера — см. README в корне, раздел «Деплой в облако»), нужно передать
и ключ: `--api-key <значение>` или переменная окружения `API_KEY`.

```bash
cd apps/spec-import-agent
npm install
cp config.example.json config.json   # serverUrl, apiKey, projectMap — по необходимости
node agent.js                         # только отчёт, в базе ничего не меняется
node agent.js --apply                 # записать изменения
```

Флаги:

- `--apply` — применить (без него — только план);
- `--drawing 2,10` — обработать только указанные чертежи;
- `--specs <папка>` — другая папка со спецификациями (по умолчанию `../../specs`);
- `--server <url>` — адрес сервера (иначе `serverUrl` из config, `ME_SERVER_URL` или `http://localhost:4000`);
- `--api-key <ключ>` — ключ доступа к API (иначе `apiKey` из config или переменная окружения `API_KEY`); нужен, только если на сервере задан `API_KEY`;
- `--report отчёт.json` — сохранить отчёт в JSON;
- `--prune` — удалять позиции, исчезнувшие из BOM чертежа;
- `--prices <файл>` / `--no-prices` — свод цен (по умолчанию `../../export/price_import.json`) / пропустить этап;
- `--config <файл>` — другой файл конфигурации (без него агент работает с настройками по умолчанию).

Тесты (разбор реальных файлов из `specs/` и правила сравнения):

```bash
npm test
```

## Ограничения

- `GET /api/components` отдаёт не больше 500 позиций — при большем
  каталоге агент предупредит; тогда понадобится серверный поиск по
  артикулу.
- Проверено на локальном PostgreSQL + сервере из `apps/server` на всех 12
  чертежах (первый прогон → 10 новых проектов, 49 позиций каталога, 102
  строки спецификаций, 12 чертежей: 117 разъёмов, 519 строк распиновки,
  168 замечаний; повторный прогон → 0 изменений).
