# Модельная электрика

Система управления проектами разработки модельной автомобильной электропроводки.
Этап 1: дашборд, список проектов, статусы процессов, журнал изменений.
Этап 2: страницы проектов (комплектующие/поставщики/фото/конкуренты),
общий каталог комплектующих, поставщики и кроссировки с историей цен,
импорт прайс-листов (в т.ч. через Local Import Agent) и выгрузка в Excel.

## Стек

- **Frontend**: React + TypeScript + Vite, Tailwind CSS v4, компоненты в
  стиле shadcn/ui (см. «Важное отступление от ТЗ» ниже), TanStack Table,
  TanStack Query, React Router, Lucide Icons.
- **Backend**: Node.js + TypeScript + Express, REST API, Zod-валидация.
- **БД**: PostgreSQL + Prisma ORM. Все статусные поля — строки, допустимые
  значения живут в коде (`statuses.ts`), а не в enum схемы: так набор
  значений любого процесса меняется без миграции.

## Структура репозитория

```
apps/
  server/             — Express API + Prisma + PostgreSQL
  web/                — React-клиент (Vite)
  local-import-agent/ — локальный CLI-агент для чтения прайс-листов
                        поставщиков с диска (см. его README)
```
Общий npm-workspace сознательно не настраивался (независимые
`package.json` — так на старте проще ставить/запускать по отдельности);
если проект вырастет, следующий шаг — вынести `statuses.ts` и общие типы
в пакет `packages/shared`, на который сейчас ссылаются `apps/*/src/lib/`
как на дублирующиеся копии с комментарием об этом.

## Запуск (два терминала)

Нужен PostgreSQL. Либо свой локальный сервер, либо (проще для этого
проекта — агенты и веб должны видеть одни данные) сразу тот же адрес,
что и в облаке после деплоя (см. «Деплой» ниже) — тогда отдельной
локальной базы не нужно вовсе.

### 1. Сервер (API + БД)

```bash
cd apps/server
cp .env.example .env        # впишите свой DATABASE_URL (postgresql://...)
npm install
npm run prisma:migrate       # применяет миграции
npm run seed                  # демо-данные (6 проектов, каталог, поставщики)
npm run dev                   # http://localhost:4000
```

### 2. Веб-клиент

```bash
cd apps/web
npm install
npm run dev                 # http://localhost:5173, проксирует /api на :4000
```

Открыть `http://localhost:5173`.

### Продакшн-сборка (без Docker)

```bash
cd apps/web && npm run build     # статика в apps/web/dist
cd apps/server && npm run build
DATABASE_URL=... npx prisma migrate deploy
DATABASE_URL=... npm start        # отдаёт и API, и apps/web/dist с одного порта
```

## Деплой в облако (доступ с телефона, постоянные данные)

В репозитории есть `Dockerfile` (корень репо) — один образ, который
собирает веб-клиент и сервер и отдаёт всё с одного порта (без CORS,
удобно с телефона). Самый простой вариант — **Railway**:

1. Зарегистрироваться на [railway.com](https://railway.com), создать
   новый проект → **Deploy from GitHub repo** → выбрать этот
   репозиторий. Railway сам увидит `Dockerfile` в корне и соберёт образ.
2. В том же проекте: **+ New → Database → PostgreSQL** — Railway сам
   пропишет сервису `DATABASE_URL` (ничего вручную вводить не нужно).
3. Зайти в сервис → **Variables** и добавить volume под фото проектов:
   **Settings → Volumes → New Volume**, mount path `/app/uploads`
   (без этого загруженные фото будут пропадать при каждом новом деплое).
4. **Settings → Networking → Generate Domain** — получите публичный
   `https://....up.railway.app`, он и открывается с телефона/откуда
   угодно.
5. При первом запуске контейнер сам применит миграции
   (`prisma migrate deploy` — часть команды запуска в `Dockerfile`) и
   создаст пустые таблицы. Чтобы наполнить демо-данными — один раз
   выполнить `npm run seed` через Railway Shell (или пропустить, если
   начинаете с чистой базы и будете наполнять её через UI/агентов).
6. Каждый `git push` в `main` — Railway пересобирает и передеплоивает
   автоматически (если включён auto-deploy, он включён по умолчанию).

Render — тот же принцип (Web Service из Dockerfile + managed Postgres +
persistent disk на `/app/uploads`), на бесплатном плане Postgres живёт
90 дней, для долгоживущего проекта лучше сразу платный план или Railway.

## Важное отступление от ТЗ: shadcn/ui

CLI `shadcn` (`npx shadcn init`/`add`) обращается к `ui.shadcn.com` за
registry — в этом окружении сетевая политика блокирует этот хост (403 на
уровне прокси), поэтому инициализировать проект официальным генератором
не удалось. Решение: компоненты `apps/web/src/components/ui/*` написаны
вручную, но по тому же паттерну, что использует сам shadcn/ui (Radix UI
primitives + `class-variance-authority` + `tailwind-merge`, без
дополнительной runtime-зависимости от самого shadcn). Внешне и по API
это тот же набор компонентов (Button, Input, Select, Dialog, Sheet,
DropdownMenu, Popover, Checkbox, Table, Tabs, Badge, Card, Separator,
Label). Как только сетевой доступ к `ui.shadcn.com` будет открыт
(Settings → Network access окружения), можно подключить и официальный
CLI — он не станет конфликтовать с этими файлами, так как использует
тот же путь `src/components/ui`.

## Модель данных

**Project** — название, артикул, ответственный, общий статус
(`active|waiting|ready|completed|cancelled`), 7 независимых статусных
полей процессов, плановая дата. `progress` (0–100%) и `nextAction`
(следующий незакрытый процесс) — не хранятся, а вычисляются на лету на
сервере при каждом ответе API (`GET /api/projects`, `GET
/api/projects/:id`), чтобы не рассинхронизироваться с реальными
статусами.

**ChangeLogEntry** — одна запись на каждое изменённое поле при
`PATCH /api/projects/:id` (поле, старое/новое значение, когда). `changedBy`
сейчас всегда `"Jarvis"` — полноценной системы пользователей/авторизации
в этом этапе нет, поле зарезервировано под неё.

### Допущения по статусам процессов

В ТЗ списки статусов для «Заказа разъёмов» и «Оплаты» явно заканчиваются
значением **«Не требуется»**, а список для «Поставки» обрывается на
**«Проблема»** — похоже на обрезанный конец сообщения. По аналогии с
двумя соседними процессами в «Поставку» тоже добавлено «Не требуется»
(`apps/server/src/statuses.ts`, `SUPPLY_STATUSES`) — без этого проект, где
поставка не нужна (например, завершённый без доп. оснастки), не мог бы
показать 100% прогресса. Если это допущение неверно — поправить набор
значений там же, в одном месте.

Отдельных наборов статусов для «Заказа оснастки» / «Поставки оснастки» в
ТЗ не было — по аналогии со связкой «разъёмы» они используют те же
наборы (`ORDER_STATUSES` / `SUPPLY_STATUSES`), что и соответствующие
процессы по разъёмам.

## API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/projects` | список всех проектов (сортировка/фильтрация — на клиенте через TanStack Table, датасет небольшой) |
| GET | `/api/projects/:id` | один проект |
| POST | `/api/projects` | создать |
| PATCH | `/api/projects/:id` | частичное обновление, пишет записи в журнал на каждое изменённое поле |
| GET | `/api/projects/:id/changelog` | история изменений одного проекта |
| GET | `/api/changelog?limit=` | глобальный журнал по всем проектам |

Эндпоинта `DELETE` нет — удаление проектов не входило в границы этого
этапа.

## Что входит в этот этап / что нет

Сделано по ТЗ: дашборд с 6 кликабельными KPI, таблица со всеми 14
колонками (сортировка, Excel-подобные фильтры по каждой колонке —
текстовые/множественный выбор/диапазон дат, скрытие колонок, изменение
ширины, закрепление колонки с названием, горизонтальная прокрутка,
постраничная навигация, инлайн-редактирование статусов, сохранение
настроек таблицы в localStorage), боковая панель проекта, создание и
редактирование проекта, журнал изменений (в боковой панели и отдельной
страницей), расчёт прогресса/следующего действия.

Страница проекта (`/projects/:id`) — 7 вкладок: Обзор/Комплектующие/
Поставщики/История рабочие (см. Этап 2 ниже), Закупки/Электросхемы/
Оснастка — маршруты-заглушки под следующий этап.

## Известные ограничения

- Нет авторизации/пользователей — `responsible` это свободный текст, не
  учётная запись; `changedBy` в журнале всегда `"Jarvis"`.
- Нет серверной пагинации/фильтрации — при реальном росте до тысяч
  проектов `GET /api/projects` стоит будет разбить на страницы.
- JS-бандл фронтенда ~530 КБ (до gzip) — для этого объёма экрана и
  компонентов это некритично, но при росте числа страниц стоит
  рассмотреть code-splitting по маршрутам.
